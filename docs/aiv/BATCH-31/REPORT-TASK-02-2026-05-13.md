## Deliverables

### 1. `BrowserLLMClient` — `src/super_browser/agent/llm/browser_transport.py`

Thin-wrapper LLM client that implements the `LLMClient` protocol by routing all API calls through `BrowserFetch` instead of the native OpenAI/Anthropic SDKs.

**Key design decisions:**

| Decision | Rationale |
|----------|-----------|
| Thin wrapper over SDK injection | The OpenAI SDK creates its own `AsyncOpenAI` client internally — injecting a custom httpx transport is fragile. Building raw HTTP requests and sending them through `BrowserFetch` is simpler, SDK-free, and works for any provider. |
| Dual-provider support | Handles both OpenAI (`/v1/chat/completions` with Bearer auth) and Anthropic (`/v1/messages` with `x-api-key` + `anthropic-version` header) API formats. |
| Same response schema | Returns identical dict shapes (`{"action": ..., "params": ..., "tokens": {...}}`) as `OpenAILLMClient` and `AnthropicLLMClient`, ensuring drop-in compatibility. |

**Methods implemented:**

- `propose_action(prompt, *, tools)` → `dict` — routes chat completion via BrowserFetch
- `create_plan(instruction, *, tools)` → `list[dict]` — system+user message via BrowserFetch
- `replan(*, instruction, original_plan, failed_step, error)` → `list[dict]` — plan revision via BrowserFetch

**Internal helpers:**

- `_call_api(body)` — builds the HTTP request and calls `BrowserFetch.fetch(url, init)`
- `_call_api_with_system(system_prompt, user_content)` — builds provider-specific message format
- `_build_request_params()` — returns URL + headers per provider
- `_extract_tokens(response_data)` — handles both OpenAI and Anthropic usage key names
- `_parse_propose_action(response_data)` — handles both OpenAI `choices` and Anthropic `content` block formats
- `_parse_plan_response(response_data)` — extracts text, strips code fences, parses JSON
